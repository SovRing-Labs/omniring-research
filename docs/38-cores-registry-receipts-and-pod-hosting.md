anything."* The direction for the week: *"what's your view of the agent in the loop model? where an agent as commnad just dispatches and
reviews, sometimes steps in"* — the agent plans, cores do the repeated work and leave receipts.

## Core contract v1, registry, receipts (the `core-registry` program)

- **Description.** One SQLite file (WAL) holds the registry, one append-only JSONL file holds the receipts. Table `cores`: `core` (dotted id, primary key, for example `doctor.wall`, `math.kb`), `version` (for the seed rows a 12-hex hash of the binary or script, `bin:<hash>`; other registering scripts write a label such as `math-kb-0` or `tchew-sessions-0`), `owner`, `kind` in {cli, socket, http, mcp}, `entry` (argv template as JSON for cli, socket path, URL or tool name), `gate` (runnable proof, exit 0 = healthy), `status` in {live, dormant, retired}, `added_ts`, `last_fired_ts`. Table `ops`: `(core, op)` key, `args_schema` (JSON list; types path | int | str | json; extras required, repeat, flag, positional, sep), `returns` (what a receipt's `output_ref` points at), `deterministic` flag.
- **Receipt** (one JSON object per line): `v, ts, core, version, op, caller, input_hash, output_ref, output_hash, gate, verdict, ms, tw` (plus `note` on fail or error, `argv` on a dry run). `input_hash` = sha256 of the canonical JSON (sorted keys, no spaces) of the op arguments plus the sha256 of every input path's bytes; the output path is not hashed. `output_hash` = sha256 of the output file, else of stdout. Verdicts: `pass` (exit 0), `fail` (non-zero), `error` (the core did not run: missing binary, timeout), `dry`. Each line is written with one `O_APPEND` write so concurrent writers do not interleave. The `tw` field is taken from an explicit environment variable only: reading an inherited job id stamped every fire made by a supervised server with that server's own id (found when a second program fired cores; fixed). The receipts file holds both sides of that fix: its first receipt fired by the web console carries a test harness's run name in `tw`, the two later ones carry null (`docs/appendix/part7/ch5-registry/results/receipts-sample.jsonl`, caller `raptor-ui`).
- **CLI.** `init` (create + seed, idempotent) · `list` · `show` · `ops` · `fire CORE OP --arg k=v ... [--dry]` (typed check against `args_schema`; exit 0 pass, 1 fail or error with a receipt, 2 refused with no receipt: unknown core, op or argument, missing required, bad type) · `receipts` · `gate CORE` (runs the gate in a fresh temporary directory, so a gate never writes into a results folder; receipt op `gate`) · `census` (lists candidate deterministic engines with no registry row: executables with a tier header, generator-engine domains, every tool an MCP server lists; it never registers anything). `fire` implements `kind = cli` only; socket, http and mcp rows can be registered and gated but not fired. Every row in the working registry is `cli`.
- **Post-condition (`returns.require`, additive to v1).** An op may declare that when any of a list of arguments is set, every JSONL row of its output must hold a truthy value at a dotted path (`built.verified` for the doctor's `need --emit`). A pass whose rows fail the check is recorded as `fail` with the count. Reason, as recorded in the project's change log: exit status alone gave a `pass` receipt for an emit run in which every built row was empty because the pod had no Rust compiler (that incident itself is recorded as text, not as a receipt). The mechanism is visible in the receipts: eight `doctor.need` fires on two pods carry verdict `fail` with note class `require built.verified: no output file` (`docs/appendix/part7/ch5-registry/results/receipts-sample.jsonl`; counts in `docs/appendix/part7/ch5-registry/results/receipts-summary.json`). Re-run: the suite's post-condition test passes (below).
- **Seed rows in the code:** `doctor.spec`, `doctor.wall`, `doctor.need`, `doctor.blackbox` (the doctor core's four stations, each fired as a CLI) and `tw` (the job supervisor: start, wait, kill, status): 5 cores, 8 ops (read from the seed table in the `core-registry` program).

In the `math-kb` program, `receipt()` sets `"input_hash": "sha256:" + hashlib.sha256(json.dumps(args, sort_keys=True).encode()).hexdigest(), "output_ref": None, "output_hash": None`; in the `gen-core` program, `receipt()` sets the same `input_hash` expression and `"output_hash": None`. So the hash covers the argument strings only: two `math-kb explain --rows F` fires on different contents of the same path `F` have the same `input_hash`, and the output is not bound. Measured in the receipts file (counts in `docs/appendix/part7/ch5-registry/results/receipts-summary.json`; all 18 `math.kb` and all 59 `gen.*` receipts in `docs/appendix/part7/ch5-registry/results/receipts-sample.jsonl`): of 18 `math.kb` receipts 17 have `output_hash` null (14 `explain`, 3 `check`; the one with a hash is the registry's own `gate` receipt), and of 59 `gen.*` receipts 33 have it null (26 `gate`, 5 `batch`, 2 `heldout-check`, all written by `gen-core`; the 26 `gate` receipts written by the registry carry hashes). Disclosed as an exception, not fixed. Registry-fired receipts are not affected: the suite's `test_input_hash_stable_and_content_bound` passes in the re-run below.

## Hosting cores on pods: `core-host` (ssh), `corehostd` (persistent worker), `thead-pod` (bring-up)

- **`core-host`** (laptop side). A hosts file maps a name to ssh target, port, key, cpu cap, nice level, working directory, role (cpu | gpu), pod id and a `jobs` flag. `probe` records nproc, load, memory, disk, nvcc, glibc, rustc and training processes (receipt). `sync HOST BUNDLE` rsyncs a named bundle incrementally (`doctor`: the doctor binary from the newest gated build + sources + inputs; `gen`: the generator cores). `run HOST -- ARGV` runs under `nice -n 19 taskset -c <real affinity list>` and a timeout, rewrites laptop paths under a bundle root to pod paths, and pulls `--out` / `--refused` files back to the caller's exact paths. `map HOST --jobs N --needs F -- ARGV` shards a JSONL spec file into N parallel jobs (row i to shard i mod N) and merges outputs in input order; it refuses N x cpus-per-job above the host cap; its reported seconds cover the parallel jobs only (not the upload of the shards or the download of the results). A remote core is a registry row `<core>@<host>` whose entry is `core-host run`, so `core-registry fire doctor.wall@host` yields an ordinary receipt. A host marked `"jobs": false` (the pod that runs the training school) is refused for run, map and sync by the tool itself (source: `host()` in the `core-host` program); this was added after a batch was run on the wrong pod for an hour.
- **`core-host` as used** (receipts, re-counted; `docs/appendix/part7/ch5-registry/results/receipts-summary.json`): 152 `core-host` receipts over six pod hosts: `sync` 48 pass; `probe` 9 pass and 3 error; `run` 74 pass and 17 fail; `map` 1 pass. The `probe` receipts of the 32-vCPU host record load averages of 62 to 93 on 32 cpus, a shared host.
- **`corehostd`** (pod side, the `corehostd` program, Python standard library only; the program is not shipped in this tree, its tests are). asyncio HTTP/1.1 plus an RFC 6455 WebSocket on loopback port 47820, reached through `ssh -L`. Routes (contract v1 section 4): `GET /health`, `GET /cores`, `GET /cores/receipts?last=N`, `POST /cores/{core}/{op}` with `{"args":{...},"caller":...,"priority":"interactive|fleet|background"}`, `POST /cores/{core}/gate`, `WS /cores/stream`. A request carrying a foreign `Origin` is refused 403. Receipts name `caller@pod:<host>`. **BELT v0 queue** (BELT is the name of the batching scheduler planned for omnid; only its v0, this queue, is built): one priority queue (interactive 0 > fleet 1 > background 2), N slots (default 8) refilled continuously, a per-op timeout, and a digest cache keyed `(core, version, op, input_hash)` for deterministic ops whose output is unchanged (a cached receipt is re-stamped with `cached: true`, `ms: 0`). **Budget guard**: every op runs under `nice -n 19` and `taskset` on the last N cpus of the process's real affinity list (pod cpu ids are scattered host ids; a fixed range is wrong), and the slot count drops from 8 to 4 (setting `CH_SLOTS_TRAINING`) while a process whose command line matches a training pattern exists. Op `cuda.compile`: nvcc -O3 over an architecture list to `.o` and `.ptx` plus a log, compile only. It runs as a supervised job on the pod.
- **`thead-pod`** (`up | adopt | install | school | watch | pull-school | tunnel | status | fetch | stop`; the school commands belong to the growth run, Part 7 chapter 1). `up` creates a CPU pod through the provider's REST API (asks for a typed yes; billable) and `install` runs five steps, numbered as in the install log: (1) upload the training kit, (2) the kit's install script and smoke gates, (3) a Rust compiler from the distribution package (a download-and-pipe installer is blocked by the machine's own command guard and was not worked around), (4) registry + doctor cores + `cuda.compile` + `corehostd`, (5) the kernel cores (`omnikit`) and the `ramkit` selftests. `stop` fetches results first and never terminates a pod.

- **FIELD PREDICTS.** Fan-out speed-up is bounded by the serial fraction and transfer cost (Amdahl, 1967); the planning notes expected that a shared pod's single thread is far slower than a laptop's, so the value would be width, not latency (not borne out by h3 and h4 above, where the single jobs were not slower; the speed-up there came from width and from start-up cost being paid in parallel). A priority queue with bounded workers and an exact-repeat cache is the admission-control shape of LLM serving engines (vLLM, Kwon et al., SOSP 2023; iteration-level scheduling, Yu et al., OSDI 2022); BELT v0 is that shape at job granularity, with no KV cache and no batching of work inside a job.

## Fleet loop: the agent directs, cores do the work, a console shows the receipts

- **What it is.** The agent plans and directs; repeated work runs on cores that leave receipts. Built: the registry and receipts (section 1), an HTTP face on the local server of the author's agent console, a Cores page in its web UI, and a read-only view plus a ledger in the author's terminal agent.
- **Cores routes** (module `cores_api.py` in the launcher sidecar, 361 lines, read by the authors of this section; the source ships with the launcher, not in this tree; contract v1 section 4; reads the registry through a read-only SQLite URI and fires through the CLI as an argv list, never a shell, with a timeout of 600 s by default): `GET /cores` (rows with ops and an `enforcement` flag for `guard.*` / `redteam.*`; 503 when no registry), `GET /cores/receipts?last=N` (1 to 500, oldest first), `POST /cores/{core}/{op}` with `{"args":{...},"dry":bool,"confirm":token}` (404 unknown core or op; 409 not live; 400 arguments outside `args_schema`, option-like or secret paths, or a refusal by the registry; 403 enforcement core without the unlock token; 403 foreign Origin; 502 no receipt printed; 503 CLI missing; 504 timeout), `POST /cores/{core}/gate`, `WS /cores/stream` (one tailer, 0.5 s poll by file offset, restart on truncation, shared by all clients; foreign Origin 403). Caller is stamped `raptor-ui`. The Origin check is applied to the POST and WebSocket routes; the two `GET` routes are read-only and carry no Origin check. The routes are not under the `/api/*` prefix the LAN portal proxies, so they are loopback-only.
- **Cores page** (the page component `Cores.svelte`, read by the authors; it ships with the launcher, not in this tree): three columns (the registry list, the selected core's ops with a fire form built from `args_schema` and a gate button, the receipt feed, live over the stream); verdicts shown as +1 (pass), 0 (error, the core did not run) and -1 (fail) in colour and in text; the list is a listbox with arrow-key movement, a live region announces each fire, the layout collapses to one column at 900 px width.
- **Terminal agent:** `talon cores` lists the registry and last receipts read-only; a session's tools run with the caller `talon:<session>`; a sync step tails the receipts file from a cursor kept in the session store and, for each receipt whose caller is a known session, writes one `ledger` row (reference = first 16 hex of the sha256 of the receipt line; unique per session and reference, so idempotent) and one notice message in the transcript. `talon ledger` shows the rows (the Talon sources `ledger.py` and `talon_run.py`, which ship with Talon, not in this tree).

## Route core: the dispatcher's lane router as a core

- **What it is.** Specified part by part against the author's definition of a core (the program `route_core.py` is not in this repository; this description is from the component's manual and planning notes). State space: cells (lane x task class), each with two Beta posteriors: competence (a finished or reviewable task counts 1, a model failure 0) and availability (rate limit, instant death, lost session, server stall, upstream error); infrastructure failures never lower competence. Read-out: ternary trit, +1 proven (competence Wilson lower bound >= 0.45), 0 unknown, -1 unavailable (cooling, or availability mean < 0.30 over at least 3 outcomes). Codebook: cell number at residues on moduli 7, 9, 11, 13 (9,009 cells), recalled by the Chinese remainder theorem, no scan. Motions: SAMPLE (Thompson draw of competence x availability over cells with trit not -1), COOL (a lane at -1 for 1 h, 6 h on a daily or free-tier limit), PROVE / DEMOTE, SPILL (no eligible cell goes to a paid lane). Source loop: one tick per dispatch pass; each pick leaves a replayable mark. Evaluation by the replay method for offline bandit evaluation (a policy is scored on a logged event only when its pick equals the logged one). Runs in **shadow mode** in the dispatcher: it logs its pick beside every unpinned dispatch and changes no routing; cut-over is the author's decision at 50 or more settled shadow dispatches.
- **Measured: PARTIAL.** The replay result file ships as `docs/appendix/part7/ch5-route/results/route_core0.result.json`; the program that produced it and the shadow log are not (so the thresholds above and the self-test cannot be checked against code, and the result cannot be re-run). The file records: 1,109 settled dispatches, of which 1,069 were "free" (not pinned; our reading of the field name); outcomes productive 596, model failure 138, infrastructure 223, rate-limited 152 (these sum to 1,109), so 375 of 1,109 settles (33.8 percent) were infrastructure or rate-limit failures rather than model failures. Logged policy over the 1,069 free events: productive 0.537, infrastructure loss 0.336. The core in replay (5 runs): 72.6 matched events per run on average (about 7 percent of the free events), productive rate 0.799, infrastructure loss 0.135. A baseline policy ("viability") in 1 run: 8 matched events, productive 0.5. The file's own caveat: the logging policy was not uniformly random, so matched-event rates are indicative, not unbiased. Reading: the core's rate is taken on the few events where it agrees with the logged lane and is compared with the logged policy's rate on all events, so the 0.799 against 0.537 is a hint and not an estimate of routing gain. Recorded but **unsupported**: the self-test pass with convergence 0.98 [needs `route_core.py`], and the shadow-mode log [needs the shadow log].
- **FIELD PREDICTS.** Thompson sampling converges to the best arm in stochastic bandits (Thompson, 1933; empirical study Chapelle and Li, NIPS 2011); offline evaluation by replay is unbiased when logging is uniformly random (Li, Chu, Langford, Wang, WSDM 2011); the dispatcher's logged policy is not uniformly random, so the replay estimate is biased by that amount (not corrected here).

## Guard core - designed, not measured

- **What it is (design).** Intrusion and malware detection for the author's own machine: detect and report only; any enforcement act is confirmed by the author. Parts on hand: a sandbox with write scopes and an audit stream, the job supervisor's per-job health trits, secret scanners and policy guards. Design: (1) an exact baseline by address: every executable, script, unit file and config under the machine's roots is hashed and its path mapped to a ring (residue) address, so a check is a constant-time lookup; a change must have a receipt (a version-control commit, a sandbox audit row, a dispatch artifact or a supervised job) to count as explained; (2) ternary verdicts: +1 known good (receipt matches), 0 unknown (log, then learn on approval), -1 contradicts baseline (alert); (3) unprivileged behaviour checks (listeners and spawned processes against supervisor, sandbox and service maps); (4) rules as data plus name-free equation signatures for incoming code; (5) markers of text addressed to an agent inside files it reads. Registry shape: ops under `guard.*`; firing an enforcement op from the web console requires an explicit confirm token (launcher routes, section 9).
- **Pre-stated bars (staged in the planning notes; the project's test record is empty and holds no pre-registration row):** G1 baseline build <= 60 s and lookup <= 1 microsecond; G2 >= 95 percent of real changes reconciled; G3 zero unexplained listeners on a clean day; G4 >= 90 percent of seeded samples caught and zero false alerts on the author's own repositories; false-alert rate over 7 days of normal work reported before any notification.
- **Measured: nothing (re-checked after the second file pull).** No guard program, no baseline and no result exists in this repository; the project's test record (not shipped) holds its header row only, and the working registry's dump has no `guard.*` row. The registry-seed fixtures named `guard.scan` in the Cores panel test harness are test data, not a guard core.
- **FIELD PREDICTS.** File-integrity monitors (Tripwire, AIDE) detect changes against a hash baseline and are known for alert volume on machines that change constantly; runtime rule engines (Falco) detect but do not block, with rules as data; signature rules (YARA) match patterns in files. Prediction for the bar: on a machine where code changes constantly, alerts are dominated by explained changes unless changes are reconciled with a provenance record - the reason design item (1) exists.

## Redteam core - designed, not measured

- **What it is (design).** Continuous attack on the author's own system only (localhost ports, own repositories, own agents; the target list is a closed file and the core refuses anything else). Loop: probe (attack) -> a finding is a counterexample with a reproducer -> the doctor core localises it -> a fix behind a dormant switch -> gate: the reproducer no longer works and no test is lost -> verified-fix store -> the guard core receives the finding as a rule -> the attack stays in the regression suite. Stations: surface census (listeners, tool servers, command-line programs that take outside input); coverage-guided fuzzing of the project's own HTML, CSS, JavaScript and image parsers; sandbox-escape cases against the agent sandbox (write outside scope, symlink, rename race, temp-dir abuse); prompt-injection documents against scratch agent sessions (pass = the agent quotes and refuses and the guard records -1); name-free static patterns (input to exec, unchecked index, overflowing size arithmetic); dependency advisories against lockfiles; secrets in history, working trees and session transcripts. Every attack runs inside the sandbox, a throwaway directory and a capped supervised unit, with the network off.
- **Pre-stated bars (staged; the project's test record is empty):** R0 the core refuses an off-list target 100 percent; R2 at least 30 escape cases, 0 escapes; R4 at least 20 injection documents, >= 95 percent held; R5 0 false patterns on a hand-checked sample of 20.
- **Measured: nothing (re-checked after the second file pull).** No redteam program, target list or result exists in this repository; the project's test record (not shipped) holds its header row only, and the registry dump has no `redteam.*` row.
- **FIELD PREDICTS.** Competition systems that combine language-model agents, fuzzers and exact verifiers to find, prove and patch vulnerabilities (DARPA AI Cyber Challenge, 2025) and coverage-guided fuzzing (AFL, libFuzzer) predict that fuzzing parsers of untrusted web content yields crash findings. Indirect prompt injection succeeds against unguarded tool-using agents (Greshake et al., 2023), so a 95 percent hold bar is a real test; our reading, not a published threshold.

## Embed core: a static token core distilled from a sentence encoder

- **What it is.** A table with one vector per vocabulary token: for each of nomic-embed-text-v1.5's 30,522 WordPiece tokens, the vector the teacher model returns for that token alone (mean pooled, L2-normalised). A text's vector is the L2-normalised weighted sum of its tokens' rows, weights `w_t = a / (a + p(t))` with `a = 1e-3` and `p` the token's frequency in the search corpus (SIF weighting). Variants: PCA to 256 dimensions; per-dimension dead-band ternary (`|v| < 0.5 sigma` goes to 0, others to the sign) packed 2 bits per value; a **learned** table `B` initialised at the distilled table `T` and fitted to minimise cosine distance to the teacher's vectors for whole documents plus `lambda * ||B - T||^2` (`lambda = 1e-4`) on sparse weighted bags, with the 200 query-target documents and 20 percent of the rest never fitted.
- **Contract.** None registered. As built it is a set of harness scripts (`harness/part7/ch5-embed/e1`, `e4`, `e5`, `e6`). The brief's design is an `embed model=core` operation on the embedding server's existing socket (a C++ station that tokenises, reads addresses, sums with weights and takes the sign); it was not built.
- **Gate (pre-registered, `docs/appendix/part7/ch5-embed/prereg/PREREG.md`, said by the file itself to precede any core result; not dated by version history).** Search harness `harness/part7/ch5-embed/hub3_eval.py` selection: 200 heading-to-chunk queries over the 6,194-document vault, random seed 0; same SQLite FTS5 store; reciprocal rank fusion (k = 60, top-50 lists). **Bar: hybrid(FTS + core) recall@5 >= 0.775 AND core docs/s >= 100x the encoder's** (the pre-registration says: docs/s on the vault chunks, same machine). Reported regardless: core-only recall, p50 query latency, table size.
- **G1 / e4 static core (`harness/part7/ch5-embed/e4/eval.py` -> `docs/appendix/part7/ch5-embed/results/e4/result.json`, `docs/appendix/part7/ch5-embed/results/e4/eval.log`): FAIL as registered.** The harness first reproduces the encoder arms exactly, and an independent earlier record agrees (`docs/appendix/part7/ch5-embed/results/hub3.result.json`: nomic-only 0.685, FTS-only 0.735, hybrid FTS + nomic 0.790, n = 200; that earlier run measured a hybrid p50 of 155.3 ms against its own bar of 0.745). Static core: core-only 0.355 (PCA-256 0.315, ternary 0.325); hybrid FTS + core **0.555** (ternary 0.560), below FTS alone (0.735); 73.9 docs/s; query p50 9.3 ms; table 89.4 MB f32, 1.86 MB as PCA-256 ternary. Speed against the harness's denominator: 64x (see the caveat below: the denominator is the weak point of the speed numbers). e4 times one Python loop per document (tokenise, then weight and sum rows); e5 and e6 tokenise in one batch call and embed with one sparse matrix product.
- **G2 / e5 learned table (`harness/part7/ch5-embed/e5/tokenlearn.py` -> `docs/appendix/part7/ch5-embed/results/e5/result-l0.0001-s150.json`, `docs/appendix/part7/ch5-embed/results/e5/result-l0.0001-s150-holdout.json`, logs `docs/appendix/part7/ch5-embed/results/e5/run1.log`, `docs/appendix/part7/ch5-embed/results/e5/run2-holdout.log`).** Targets inside the fit set (not an honest test, kept as a signpost): core-only 0.655, hybrid 0.760, 572.9 docs/s, p50 5.95 ms. **Hold-out (1,409 documents never fitted, including all 200 targets): FAIL as registered** - core-only 0.505, hybrid **0.640** (FTS 0.735), held-out document cosine to the teacher 0.9412 against 0.9927 on fitted documents, 478.8 docs/s, p50 10.72 ms. Read: the table memorises.
- **G3 / e6 more fitting text (`harness/part7/ch5-embed/e6/prep.py`, `harness/part7/ch5-embed/e6/fit.py`, `harness/part7/ch5-embed/e6/eval.py` -> `docs/appendix/part7/ch5-embed/results/e6/result-l0.0001-s300.json`, `docs/appendix/part7/ch5-embed/results/e6/fit.log`, `docs/appendix/part7/ch5-embed/results/e6/fitlog_l0.0001_s300.json`): FAIL as registered.** Fit set = the vault (6,194 documents) plus scrubbed chunks of the author's own agent sessions, 19,664 documents in all (the total is stated in the reservoir probe's prep harness, `harness/part7/ch5-reservoir/prep_tokens.py`, which reuses the e6 fit set's order; the session share, 13,470 chunks, follows by subtraction and equals the chewer's recorded store size of section 4; the fit-set file itself is not shipped and no checksum of it is recorded in this repository, so the counts are PARTIAL), fitted on a 16-vCPU pod, 300 steps, 206 s (last line of `docs/appendix/part7/ch5-embed/results/e6/fit.log`). Search gate: hybrid **0.600** (bar 0.775; FTS 0.735), core-only 0.425, never-fitted target cosine 0.9228, 713.6 docs/s, p50 3.96 ms. The fit log shows held-out cosine peaking at step 100 to 125 (vault 0.9396, sessions 0.9225) and then falling to 0.9173 / 0.8857 at step 299 while fitted cosine kept rising (0.9889 / 0.9878): more text did not raise the generalisation ceiling of a bag-of-tokens table, and at about 0.94 cosine to the teacher the top-50 list still drags the fused ranking below FTS alone.
- **Caveat on the speed ratios (checked against the benchmark file, shipped as `docs/appendix/part7/ch5-embed/results/embed-bench-result.json`).** The ratios divide the core's docs/s by a constant of 1.16 docs/s for the encoder, hard-coded in `harness/part7/ch5-embed/e4/eval.py` (and `harness/part7/ch5-embed/e5/tokenlearn.py`, `harness/part7/ch5-embed/e6/eval.py`) with the comment that it comes from that benchmark file. That file confirms the figure (`nomic_f16`: 1.16 docs/s, `doc_batch_s` 51.8, 768 dimensions) but not its workload: it does not state the document count, document length or machine; every recall in it is a multiple of 1/60 and 51.8 s at 1.16 docs/s is 60 documents, so it is a 60-item short-document benchmark, not the vault chunks the pre-registration names. The project's embedding-server planning notes record the encoder on the vault's own long chunks as 0.321 docs/s (a 100-chunk test) and 0.421 docs/s (the full 6,194-chunk re-embed, 14,710 s); these two figures are text records only, with no result file in this repository (PARTIAL). Against those rates the same core throughputs are 2.8 to 3.6 times larger than printed: e4's 73.9 docs/s would be 176x to 230x, not 64x. So the **speed bar of e4 ("64x, missed") depends on the denominator and is not a reliable miss**; e4 still fails the registered gate on quality (hybrid 0.555 against 0.775), and e5 and e6 fail on quality in every case. Speed ratios as printed by the harnesses: e4 64x, e5 494x (fit-set targets) and 413x (hold-out), e6 615x; the speed bar is therefore **PARTIAL**: the core is hundreds of times faster than the recorded encoder rates; the exact factor against a same-run encoder on the same chunks is not measured. The project brief records that batching the encoder through its command-line embedder is much faster per item than the server path (figures **unsupported** here).
- **e1 distillation (`harness/part7/ch5-embed/e1/distil.sh`).** The job record of the distillation (scrubbed summary `docs/appendix/part7/ch5-embed/results/e1-distil-job-summary.json`: command `bash e1/distil.sh`, exit 0, last log line `distil done: 15 parts`) gives an elapsed time of 800.5 s (13 min 20 s) for the 30,522 tokens. The project text also says 5.8 ms per token; that does not reconcile with the job: 800.5 s over 30,522 tokens is 26.2 ms per token overall, and the script restarts the embedding program once for each of 15 parts of 2,048 tokens (each start loads the model), so 5.8 ms is probably a per-token compute figure; only the 800.5 s is claimed. Recorded but **unsupported**: that the distilled vectors match the served model at cosine 1.0000 [needs the comparison output; the vocabulary part files `e1/vocab/*.emb` are not shipped].
- **Decision recorded:** search stays on the encoder; the tables are not shipped, and none of their checksums is recorded in this repository (`e1/vocab/`, `*.npy`, `*.npz` are ignored by the project's version control: `harness/part7/ch5-embed/embed-core.gitignore.txt`).
- **Open signposts, not run:** weighted fusion for the e4 to e6 tables (a weighted fusion was tried on the reservoir core of section 6, post hoc: see there); the core as a shortlist with encoder re-rank (uses the speed, not the table's ceiling); a contextual core that reads word order; ring-address reads of tokens (token id as a residue address on the ring codebook) and the decoder side (the same table read backwards); a ternary table under the learned fit.
- **FIELD PREDICTS.** Distilling a sentence encoder into a static embedding table gives up to roughly 500x CPU speed, with retrieval the weakest task, about 82 percent of a small contextual baseline (Model2Vec, Minish Lab, 2024, as recorded in the brief). SIF-weighted averages are a strong similarity baseline (Arora, Liang, Ma, ICLR 2017) but a bag cannot see order. Reciprocal rank fusion (Cormack, Clarke, Buttcher, SIGIR 2009) uses ranks only, so it cannot discount a weak list; that is a property of the method, not a published prediction of this result. Observed: speed matched the prediction once tokenising was batched (413x to 615x against the harness constant; more against the vault-chunk rate); quality fell short of the bar in every arm, and the fusion effect was visible (hybrid below FTS-only in e4, e5 hold-out and e6).

## Chewer core: session transcripts as searchable, step-sized chunks

- **What it is** (read from the source of the chewer package, which is not shipped in this tree; the tests that exercise it are). A deterministic ingest and search pipeline over the author's own agent session logs. Sources, each opened read-only: a local session database of one coding agent (`sessions.py`), a second agent's database and the author's terminal agent's store (`agents.py`). A chunk is one task step: a user prompt (text block not starting with `<`; first 4,000 characters) and what followed until the next prompt: assistant text (first 2,000 characters), each tool call (name and first 240 characters of its input) and each result (first 360 characters). Model "thinking" is excluded by default; blocks before a session's first prompt belong to no step. Every text is passed through a credential / e-mail / home-path scrubber before it is stored (the scrubber is a separate script, `chew-export`, that is not in this repository, so the scrub rules are not verified here). A step over 3,000 characters is cut into parts of 3,000 characters; every part after the first starts with the prompt's first line (at most 300 characters) and `(part k of n)`. A session's last, still-open step is never stored; a session counts closed when it has been idle more than 30 minutes (the terminal agent's store also counts a finished status). A per-session high-water mark (`ingest_state`: last line consumed, next sequence number) makes ingest incremental. Metadata (project from the project directory, date from the session's first timestamp) must be present: a session without them is refused, never guessed. Chunk id: the first 32 hex characters of the sha256 of the metadata JSON, the sequence number and the text; insertion is `INSERT OR IGNORE` on that unique id, so a rerun adds nothing. Storage is SQLite: a `chunks` table, an FTS5 external-content index over the text, and a `sqlite-vec` `vec0` table of 768-dimension float vectors keyed by the chunk's rowid. Vectors are loaded from embeddings computed on a pod (f16 encoder, mean pooling, L2), matched by rowid lists, count-checked per file, and only rowids without a vector are loaded. Search: FTS5 with bm25, where each query word is quoted and the quoted words are juxtaposed (FTS5 reads that as all words required); vector nearest neighbours; or hybrid, the two lists (top 50 each) fused by reciprocal rank fusion with k = 60. The same package also ingests timed transcripts (`.vtt`, `.srt`, `.json`, `.txt`) with a required metadata sidecar (project, date, participants), chunked by speaker turn with a 1,500-character cap. Registered as core `chew.sessions` (kind cli, entry `python -m tchew.cli`) with `pytest -q tests` (120 s timeout) as its gate (`docs/appendix/part7/ch5-registry/results/cores-registry-summary.json`).
- **Tests.** 15 test functions in four files (`harness/part7/ch5-chewer/tests/test_tchew.py` 7, `test_vectors.py` 2, `test_sessions.py` 4, `test_agents.py` 2). The registry's gate receipt of 2026-10-08 08:00 UTC records `11 passed in 1.35s` (the suite then had 11; the files hold 15). Re-run read-only in a scratch copy: 4 pass; 5 fail because the fixture transcripts are not in this repository (only the metadata sidecar `harness/part7/ch5-chewer/tests/fixtures/a.vtt.meta.json` is); 6 could not be run because the two files that import the session chunker need the scrub script that is not in this repository. The only recorded pass is 11 of the 11 tests then present; a pass of all 15 is not recorded, and a re-run here does not reach it (PARTIAL).
- **Gate (bar quoted from the planning notes; no pre-registration file ships for it): `c4` known-item recall.** 200 seeded questions (each is a chunk's own prompt, with the target stripped of its prompt text in both arms) against the same corpus. **Bar: hybrid recall@5 >= FTS + 0.05 at p50 <= 50 ms.**
- **Result: FAIL as registered** (`docs/appendix/part7/ch5-chewer/results/c4/result.json`, `docs/appendix/part7/ch5-chewer/results/c4/diag.json`; values checked against the files). n = 200. recall@5: FTS **0.150**, hybrid **0.115** (30 and 23 of 200). Search p50: FTS 72.14 ms, hybrid 70.34 ms (bar 50 ms). Both counts of the bar were missed: the hybrid was below the FTS arm instead of 0.05 above it, and p50 was above 50 ms. Query-embedding latency was not recorded (`NaN` in the result file), so the hybrid p50 covers the search only. Diagnostic after the failure (`diag.json`, verdict unchanged): vector-only recall@5 0.07, vector-only recall@50 0.19, FTS recall@50 0.325, and a top-5 hit from the target's own project and date 0.875 for the vector list and 0.935 for FTS (field names `vec_sess@5`, `fts_sess@5`): search finds the right conversation, not the right step, because neighbouring steps of one task look alike. The question-building and scoring scripts (four small scripts named in the project's test records) are not in this repository, so the result is **PARTIAL**: the numbers match the file, the harness is not here. How the FTS query was built from a prompt is therefore not verified; the shipped search function requires every query word to occur in a chunk, which for a long prompt is a harsh rule. Cheapest probe (not run): the same 200 targets with an any-word (OR) bm25 query and with a prefix of the prompt.
- **Recorded but unsupported:** ingest counts (a first run of 242 sessions to 11,942 chunks in 86 s with a zero-new rerun; a store of 13,470 chunks across three sources) are recorded in the system manual as text, not in a result file [needs a saved ingest log]. 11,942 + 114 + 556 does not give 13,470; the project brief's status log gives the first source as 12,800 chunks by then (12,800 + 114 + 556 = 13,470).
- **Not built:** ring addresses (project, session, turn as residues, to jump from the found conversation to the step); the live (streaming) firing of the core on new rows; the transcriber (audio to text with a local speech model, then the same chunker); the busy-work miner that would read these chunks for repeated tool sequences. Signposts recorded for the failure: score at task level (merge a session's steps, or return the session), a ring address to jump to the step, and a question set that is not the prompt itself.
- **FIELD PREDICTS.** None was recorded when the bar was written (the bar was set against the existing FTS baseline). Fusion method: reciprocal rank fusion (Cormack et al. 2009); with a vector list at recall@5 0.07 against FTS 0.150 the fused result below FTS (0.115) is the property of rank-only fusion noted in section 3, not a published prediction. Transcriber side, designed only: Whisper (Radford et al., 2022) via its C++ port.

## Reservoir probe: a fixed ternary reservoir over token sequences, ridge readout to the teacher's vectors

- **What it is.** A test of one of three candidate ways (liquid reservoir, holographic superposition, topological growth) to turn a core into a fine-tunable ternary model; the three are treated as layers (substrate, consolidation, growth). `harness/part7/ch5-reservoir/reservoir.py`: tokens enter through a fixed ternary input projection of the PCA-256 token table; a fixed sparse recurrent matrix `W` with K non-zeros per row (K = 8 unless stated), entries in {-1, +1} scaled by one global scalar so the spectral radius is rho (0.9 unless stated); state `x_t = tanh(rho W x_(t-1) + I[token_t])` over the first 96 tokens; features = mean state and last state (optionally plus a plain bag of the PCA-256 rows); a closed-form ridge readout fitted to the encoder's document vectors (regularisation chosen on a validation tenth of the fit rows); no gradient anywhere. A float (Gaussian) reservoir is the control. Usage `reservoir.py KIND N RHO FEATS OUT.json [K] [seed]`. Scored on the embed core's held-out split and the same 200-query gate (section 3), bar unchanged: hybrid >= 0.775 with the registered equal-weight fusion (k = 60).
- **Contract.** None registered; a probe (`harness/part7/ch5-reservoir/prep_tokens.py` builds the token sequences in the embed core's document order, 19,664 documents).
- **Results (200 queries; harness `harness/part7/ch5-reservoir/reservoir.py`; results `docs/appendix/part7/ch5-reservoir/results/s1/*.json`; seed 1 unless stated).** FTS-only 0.735 in every arm. All ten arms **FAIL the 0.775 bar** (`"PASS": false`). The first five arms:

- **Reading, as measured.** (a) Against the embed core's learned table (hybrid 0.600, core-only 0.425) every arm is better (0.705 to 0.765 hybrid), but the **hybrid recall does not separate the arms**: the same configuration (K = 16, rho 0.95) scores 0.765 with seed 1 and 0.705 with seed 2, a spread of 12 queries out of 200, larger than every difference between arms (the no-reservoir bag control 0.745 against the best arm 0.765 is 4 queries; the whole sweep of N = 1024 reservoir + bag arms spans 0.740 to 0.765). A rate near 0.75 on n = 200 has a standard error of about 0.03. Core-only recall (0.565 to 0.605 for N <= 1024) and held-out cosine (0.8938 to 0.8949 for all N = 1024 reservoir + bag arms, including both seeds) barely move, so the swing in the hybrid number is rank tie-breaking in the fusion of two weak lists, not a change in the representation. The project's test records label the 0.765 run a record; with the seed-2 run it is not distinguishable from the bag control. The probe does not show the reservoir adding retrieval quality; it shows that a ridge readout fitted as here beats the previous learned table. (b) Ternary and float reservoirs agree at N = 1024: held-out cosine within 0.0008 (vault), hybrid 0.750 vs 0.745 (one query). One configuration and one seed for that comparison; it is not a general statement about ternary reservoirs. (c) N = 2048 is worse (19,664 documents in all across fit and held-out; the regularisation search chose 0.1), so more units did not help here. (d) The reservoir alone (0.725 hybrid) is below FTS-only (0.735). (e) The held-out document cosine of every arm (0.877 to 0.895 on the vault split) is below the learned table's final held-out cosine in section 3 (0.917 at step 299, 0.940 at peak) while its core-only retrieval is higher; both harnesses read the same fit-set file for the fit mask, but cosine to the teacher and retrieval recall moved in opposite directions between the two methods, and no analysis of why was run. (f) Connectivity K = 8, 16, 32 gave hybrid 0.750 / 0.760 / 0.740 and core-only 0.580 / 0.575 / 0.605; spectral radius 0.90, 0.95, 0.98 at K = 16 gave 0.760 / 0.765 / 0.760: no trend beyond the seed spread.
- **Weighted fusion on the peak reservoir (`harness/part7/ch5-reservoir/eval_opt_a.py` -> `docs/appendix/part7/ch5-reservoir/results/s1/option_a_sweep.json`) - post hoc, not a pass.** The harness rebuilds the K = 16, rho 0.95 reservoir (seed 1) and grid-searches the fusion rule over 100 settings (rrf constant 20, 30, 40, 60 x FTS weight x core weight, five values each) on the **same 200 queries as the gate**. Best recall@5 **0.800**, reached by six settings (one has constant 20, weights 1.0 and 0.6; the file's `best_params` lists the first of the six, constant 20, weights 0.8 and 0.4); 58 of the 100 settings reach 0.775 or more; the registered rule (equal weights, k = 60) scores 0.760 in this harness (0.765 in `reservoir.py`: the two implementations of the same reservoir differ by one query). The best settings give the core list half to about seven tenths of the FTS list's weight. The project's test records label this "gate cleared"; **it is a maximum over 100 settings chosen on the gate's own queries, with one reservoir seed (the other seed scored 0.705 under the registered rule), so it is optimistic and does not pass the registered bar.** It does agree with the section 3 reading that rank-only fusion cannot discount a weak list: down-weighting the core list helped. Cheapest probe (not run): fix the weights on this query set, score them on a second set of 200 queries from a different random seed, with two or more reservoir seeds.
- **s3 / s4 probes (`harness/part7/ch5-reservoir/s3/vsa_probe.py`, `harness/part7/ch5-reservoir/s4/spline_probe.py`; results `docs/appendix/part7/ch5-reservoir/results/s3/s3_vsa_summary.json`, `docs/appendix/part7/ch5-reservoir/results/s4/s4_spline_summary.json`; numpy only, synthetic data).** Two small probes of the other two layers exist; they are **not** the tests registered in the planning notes (for the second layer: held-out accuracy on job A before and after job B; for the third: the generators' verifiers as fitness with a frozen replay that loses nothing), which remain not run. What they measure:
  - *s3, holographic memory.* A bipolar accumulator of dimension 8,192 stores bound condition-remedy vectors by addition and reads them by unbinding and nearest-symbol cleanup. 50 incident-remedy pairs added one at a time (10 hand-written, 40 generated names): retention of all earlier pairs 100 percent after each addition, minimum cosine margin 0.0876 at 50 pairs. Capacity, 50 random pairs sampled at each size (the sampler is unseeded, so a re-run differs): recall 100 percent up to 200 stored pairs, then 92, 76 and 54 percent at 300, 400 and 500 in the packaged result (a read-only re-run gave 98, 94, 64 and 64 percent at 200 to 500). "One-shot correction": a synthetic query that ranks the target document 92nd is moved to rank 0 by adding 0.3 times that document's vector; the scores of the other 99 documents shift by at most 63.0 and 19.0 on average in dot-product units, so interference is not zero. The memory is a separate store, not the reservoir's readout, and the correction targets the document by construction.
  - *s4, sprouted cluster.* A 256-node ternary reservoir reads a three-class synthetic health signal (test accuracy 0.945). A planted fault signature on two input channels is invisible to it; a 32-node cluster whose input weights are set by hand to those two channels, with a readout fitted by ridge, reaches 0.99 on the novel fault (test), 0.96 after pruning 8 of the 32 nodes; growth 24/256 = 9.38 percent. A re-run read-only gave an identical result file. Two reading notes: the file's `novel_fault_acc_before` of 1.0 is the share of the 300 novel samples that the base readout predicts as "normal" against all-zero labels, not an accuracy on the fault; and the base-task invariance check (difference 0.0000, "zero forgetting") recomputes the same untouched base readout on the same states, so it holds by construction and could not have failed.
- **Not built / not measured:** the registered second- and third-layer tests above; a spectral-radius or sparsity sweep beyond the values listed; more than two seeds; an echo-state check; the reservoir fused with learned weights on a held-out query set. Superposition into a reservoir's readout and growth under a verifier are therefore open.
- **FIELD PREDICTS.** Echo state networks and liquid state machines use a fixed random recurrent network with a trained linear readout (Jaeger, 2001; Maass, Natschlager, Markram, 2002). Reservoirs with very low weight resolution lose accuracy and more units compensate (Busing, Schrauwen, Legenstein, 2010, as recorded in the planning notes); no direct benchmark of {-1, 0, 1} reservoirs was found when they were written. "Liquid time-constant" networks (Hasani et al., 2021) are gradient-trained neural ODEs, a different thing. Observed: ternary matched float at one size (consistent with the prediction); more units did not compensate at N = 2048 on this data; the seed-to-seed spread of the hybrid number (0.06) is larger than any between-arm difference measured.

## Reading
A bag of tokens has a generalisation ceiling near 0.94 cosine to its teacher, and at that ceiling rank fusion drags the result below full text
